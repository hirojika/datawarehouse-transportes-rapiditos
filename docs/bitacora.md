## 04-11-2026: cambio de stack y migración del Avance N°1 a PostgreSQL

### Decisión de stack

Se eligieron las herramientas por mérito técnico y por su facilidad de automatización: todo en texto versionable, ejecutable por línea de comandos y con pruebas automáticas.

| Capa | Antes | Ahora | Motivo principal |
|---|---|---|---|
| DWH | MariaDB (XAMPP) | PostgreSQL 17 en Docker | Esquemas (`stg` y `dwh` en una base), DDL transaccional, `CHECK` que se cumplen, funciones analíticas (`GROUP BY CUBE`, `FILTER`, vistas materializadas) |
| Administración | phpMyAdmin | pgAdmin 4 en Docker | Web, igual en Linux y Windows; su ERD Tool exporta el esquema estrella como imagen |
| ETL | Python + Talend Open Studio | Python (extracción) + Apache Hop (ETL) | Pipelines en XML versionables y ejecución sin interfaz con `hop-run`; Talend Open Studio está descontinuado desde 2024 |
| Cubo | Sin definir | Cube (Cube Core) | Dimensiones y métricas definidas en YAML, con API SQL y REST |
| Dashboard | Streamlit + Plotly | Sin cambios | Solo código, funciona en Linux y Windows |
| Entorno | XAMPP | Docker Compose + `venv` | Mismo ambiente para todo el grupo con un comando |

Se evaluó dbt como alternativa a Apache Hop (transformaciones en SQL, pruebas declarativas y documentación del linaje). El grupo prefirió Apache Hop.

Hop (Fase 2) y Cube (Fase 3) se instalan cuando se llegue a esas fases.

### Migración del Avance N°1 a PostgreSQL

El modelo dimensional no cambió: el proceso de negocio, el grano, las 6 dimensiones, las 7 FK y las medidas son los mismos. Cambió su implementación física (detalle en `docs/modelo_dimensional.md`, sección 8):

| Tema | Decisión | Motivo |
|---|---|---|
| Tipos | `SMALLINT`, `INTEGER`, `BIGINT`, `NUMERIC`, `BOOLEAN` | PostgreSQL no tiene tipos sin signo ni `TINYINT` |
| Valores no negativos | `CHECK` en cantidad, montos, distancia, duración, peso y edad | Reemplazan a `UNSIGNED` y además se cumplen de verdad |
| Consistencia de montos | `monto_neto = monto_bruto − monto_descuento` y descuento entre 0 y el bruto | Apunta al criterio "DWH poblado sin errores de consistencia" |
| Consistencia de `dim_tiempo` | Cada atributo derivado (día, mes, semana ISO, trimestre, etc.) debe coincidir con `fecha` | La dimensión no puede quedar inconsistente aunque el ETL falle |
| Dominios cerrados | `tipo_cliente` ('persona', 'empresa'), `tipo_servicio` ('pasajeros', 'carga') y `linea_negocio` (las 6 líneas literales del enunciado) | Evita variantes de escritura que separen grupos en el cubo |
| `cantidad` | `CHECK (cantidad >= 1)` | Una compra tiene al menos una unidad |
| Llaves sustitutas | `GENERATED BY DEFAULT AS IDENTITY` | La base las genera, pero Hop puede insertar una llave propia si la necesita |
| Nombre de la PK | `pk_<tabla>` | PostgreSQL respeta el nombre (MariaDB lo cambiaba a `PRIMARY`), así la norma se cumple al 100 % |
| Prefijos nuevos | `ck_<tabla>_<columna>` (CHECK) e `ix_<tabla>_<columna>` (índices) | Mantener la nomenclatura normada |
| Índices | Uno por cada FK de `fact_venta` | PostgreSQL no indexa las FK por su cuenta |
| Organización | Base `rapiditos`, esquema `dwh` (en la Fase 2 se suma `stg`) | Separar staging y DWH sin usar dos bases |
| Re-ejecución | `BEGIN` + `DROP SCHEMA IF EXISTS dwh CASCADE` + `CREATE SCHEMA dwh` … `COMMIT` | Si una sentencia falla, no queda nada a medias |

### Cómo funciona el script

- Maneja el pgAdmin real de `docker-compose.yml` con Chromium sin interfaz (Playwright 1.64.1), conectado a la base `rapiditos`. Las capturas son de la herramienta real, con datos reales del catálogo.
- Usa un usuario de pgAdmin propio, `capturas@rapiditos.cl`, que crea al empezar y borra al terminar con el `setup.py` del contenedor. Así no toca el espacio de trabajo del usuario admin, que tenía un ERD sin guardar.
- La captura 02 vuelve a ejecutar `sql/01_ddl.sql` en `rapiditos`. Antes revisa que ninguna tabla de `dwh` tenga datos y, si alguna tiene, se detiene sin hacer nada.
- La captura 01 es la salida real de `docker compose ps` dibujada con aspecto de terminal, no una foto de una ventana. Así lo indican también el pie de la figura y `docs/checklist_capturas.md`.
- Para las capturas 05 se ejecuta cada consulta de `sql/99_validacion.sql` por separado. La ventana y el divisor entre editor y resultados se ajustan para que se vean la consulta completa y todas las filas, y se ensanchan las columnas cuyo texto quedaba cortado.
- Se ejecuta con `python herramientas/capturar_pgadmin.py` y tarda unos 2 minutos. Hay que volver a correrlo si cambian `01_ddl.sql` o `99_validacion.sql`.

Problemas resueltos al armarlo:

| Problema | Solución |
|---|---|
| pgAdmin recuerda qué nodos del árbol quedaron abiertos | Usuario nuevo en cada ejecución, y cada nodo se expande solo si su hijo no se ve |
| El Query Tool vive en un iframe cuya URL a veces es `about:srcdoc` | Se identifica por tener un editor (`.cm-content`) |
| El texto de éxito en pantalla puede ser el de la consulta anterior | El fin se detecta en las respuestas de `/sqleditor/poll/` |
| `time.sleep` impide que Playwright entregue los eventos de red | La espera se hace con `pag.wait_for_timeout` |
| Los avisos flotantes tapaban filas; están en la página principal, no en el iframe | Se cierran antes de cada captura |
| pgAdmin calcula mal el ancho de las columnas, y la preferencia "por contenido" no lo corrigió | Se mide cada texto con un canvas y se arrastra el borde del encabezado |
| Al iniciar sesión, un usuario nuevo recibe el aviso "'Server Name' cannot be empty" | Es de pgAdmin, aparece antes de conectarse y no afecta las capturas |
